01
the receipt, itemised

Nobody wrote 3.4 GB of code.
The build system did.

target/debug is not "your program". It is a warehouse of intermediate representations: static libraries for every dependency, a query-database of partial compilation state so the next rebuild takes 2 seconds instead of 200, and a complete symbolic description of every generic instantiation the debugger might ever ask about.

misread #1

"It's a cache. Caches are supposed to be big."

True — and that is exactly the point. A cache is spent work kept for reuse. Rust keeps it on your laptop, in your project folder, visible in du. C++ keeps the same kind of work inside libfoo.so, foo.lib and /usr/lib — built once, on a maintainer's CI, and shipped to you as a "dependency" of a few megabytes.

misread #2

"Release builds are what matter."

target/release for the same project is ~1.6 GB, and the shipped executable is ~30 MB. The 3.4 GB is the development loop tax — the price of "edit, hit run, see a window in 4 seconds". Every ecosystem pays that tax. Only some of them hide the invoice in a tarball.

misread #3

"C++ wouldn't need all this."

C++ needs more. It just doesn't need it in your checkout. Turn the page.

02
a project of the same scale

The C++ binary is 16 KB.
Here is the invoice you didn't receive.

where the C++ bytes actually live
  • TOOLCHAIN

    The compiler itself is a gigabyte-scale C++ program. Clang/LLVM installed: 1.5–3 GB. MSVC + Windows SDK: 7–12 GB. You don't build it — Microsoft and the LLVM project did, and they are a very large C++ project whose build directory is 25 GB.

  • STL / CRT

    libstdc++, libc, the dynamic loader: prebuilt, preinstalled, shared by every process on the machine. The 16 KB binary is small because it is not self-contained.

  • HEADERS

    Header-only libraries (Boost, Eigen, nlohmann, glm, Asio) ship source, not binary — and get recompiled into every translation unit that touches them. This is the part C++ and Rust share: monomorphisation is paid per use site, always.

  • SYMBOLS

    Ship the PDB / .dSYM / .debug and the binary is no longer 16 KB. A game's symbol server runs into hundreds of gigabytes — the same DWARF that inflates Bevy's target/.

the honest sentence

"A C++ project of the same scale would not produce much smaller intermediates. It would produce none at all — on your machine."

03
the great hiding place

Binary distribution didn't remove the cost.
It moved the cost out of sight.

Because C++ is genuinely hard to build — no standard package manager, no stable ABI, a combinatorial configuration matrix — the ecosystem converged on shipping prebuilt binaries: apt, Homebrew, vcpkg, Conan, vendor SDKs, DLLs next to the .exe. That decision is why "C++ feels lean". It is also the source of a distinct and severe class of problems.

      interactive · the combinatorial trap

      A prebuilt binary is a point in a matrix, not a package.

      when the bill arrives anyway

      Six lines of Python.
      Four point four gigabytes.

      Python is the counter-example that proves the rule. It has perfect binary distribution — wheels, PyPI, pip install and it works. And because the binaries are huge native runtimes (CUDA, cuDNN, oneDNN, MKL, Triton) rather than compiled-from-source libraries, the cost reappears as bandwidth and disk, multiplied by every environment you ever create.

      interactive · the multiplication

      Binary distribution is paid per environment, not per project.

      Every venv, every conda env, every Docker image, every CI job without a warm cache, every student laptop in a lecture hall re-materialises the same 4.4 GB. Caches and hardlinks help on one machine. They do nothing for bandwidth, and nothing at all across machines.

      root causes, language-agnostic

      Six reasons the bytes exist
      in every compiled language.

      the actual dividing line

      It was never "Rust vs C++". It's ship-the-machine-code vs ship-the-recipe.

      A JVM library ships bytecode once; the runtime is shared and already installed; a Spring Boot fat jar is 40 MB and its dependencies are 40 MB of portable bytecode usable by every project on the box. A .NET assembly is the same. Go compiles to machine code but has no generics explosion of the C++/Rust kind, a fast linker and a shared build cache in $GOCACHE — hello world builds in 0.3 s from a 300 MB cache. Rust and C++ sit at the other extreme: every user recompiles the world, and gets maximal runtime performance and zero runtime dependency in exchange.

        the ecosystem-level fixes

        Cranelift as an alternative codegen backend (-Zcodegen-backend=cranelift) cuts debug build time dramatically at the cost of slower runtime code. sccache and a shared CARGO_TARGET_DIR deduplicate work across projects — which is precisely the trick binary distribution uses, applied at the level of your cache instead of a distro's. Rust is converging on C++'s answer: build it once, share the artifact. That's what a build cache is.

        closing argument

        The bytes were always there.

        Compiled software of any real size requires gigabytes of intermediate machine code, debug information and monomorphised templates. That is physics plus a design choice about static linking. The only question is who holds the bytes, when, and how many copies exist.

        rust pays

        Up front, locally, in full — on every developer's SSD, for every project, visibly. Enormous disk and first-build cost; in exchange: reproducible builds, no ABI, one artifact per source revision, and no DLL hell.

        c++ pays

        Deferred, centrally, invisibly — by distro maintainers, vendor CI, and package-manager build farms. Cheap for you, until you need a configuration nobody published. Then you pay the whole 25 GB yourself, at 3 a.m., with a linker error.

        python pays

        In bandwidth and duplication, per environment, forever. Three lines of import is a 4.4 GB download — and because the binaries are opaque native blobs, you cannot shrink them, only cache them.
