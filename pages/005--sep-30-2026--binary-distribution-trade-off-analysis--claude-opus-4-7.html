Why your Bevy “Hello World” weighs 4 gigabytes — and C++ is barely any better.

A short essay on source distribution, binary distribution, the debug information no one asked for, and the reason PyTorch quietly consumes half your SSD.

Disk Full

by an engineer who ran
du -sh target/ once too often

The scene of the crime

A brand-new project

# You did nothing wrong. $ cargo new hello --bin $ cd hello $ cargo add bevy $ cargo run # ... 400+ crates compile ... # ... coffee ... # ... more coffee ... $ du -sh target/ 4.2G target/

Four gigabytes. For a window that says Hello, world. Your src/main.rs is seven lines long.

There is a rite of passage in modern Rust game development. You type cargo add bevy, press enter, and watch as your laptop transforms into a small space heater. Half an hour later, you own a target/ directory that is larger than the entire Windows XP installation media — and all you have to show for it is a spinning cube. It is tempting to blame Bevy, or Rust, or the compiler team. The truth is more interesting: what you are looking at is source distribution taken to its logical conclusion, and it is the price of a genuinely reproducible, hackable, cross-platform build.

To understand why, we need to open up that target/ folder and stop treating it as a black box. Almost none of those 4 GB are your program. Almost all of them are things the compiler needed once and might need again.

1 · Anatomy of a 4 GB target/

Rust · Bevy 0.14-ish

Approximate breakdown of a fresh cargo run of a Bevy "hello window", debug profile. Yours will vary; the shape will not.

WhatRough sizeShare
Debug info (.rlib, .pdb, DWARF) ~2.2 GB
Incremental compilation cache ~800 MB
400+ dependency .rlibs ~600 MB
Proc-macro artifacts, build scripts ~200 MB
Actual hello executable ~90 MB
Your source code ~180 bytes (a rounding error)

Where did it all go?

Every one of those 400+ crates — wgpu, naga, winit, glam, serde, tracing, and 395 friends — is compiled from source, for your exact target triple, with your exact feature flags, in debug mode, with full debug symbols, and cached so that the next build is fast.

The compiler keeps: the object files, the metadata needed for cross-crate inlining and generic instantiation (MIR), incremental fingerprints, and multiple copies of essentially the same generic code monomorphized for different types. Bevy is heavily generic. So is wgpu. So is basically all idiomatic Rust. Every Query<(&Transform, &Velocity)> in your code is a new function in the binary.

Strip the debug info and run --release, and the executable falls to a few tens of megabytes. But target/ is not the executable. It is the workshop.

2 · “But C++ doesn’t do this!” — well, actually…

The popular counter-argument is that a C++ project “of the same scale” produces a tiny build directory. This is a comforting myth. If you actually build a comparable C++ game — say, a minimal SDL2 + bgfx + glm + spdlog + fmt + entt program — from source, in Debug, with symbols, the numbers line up depressingly well:

BuildIntermediate size
Bevy hello (debug, from source)~4.2 GB
Unreal C++ project (Debug)80–150 GB
Chromium (Debug)100+ GB
LLVM + Clang (Debug)30–60 GB
Small SDL2+bgfx demo (Debug)1–3 GB
Same demo, Release + stripped40–120 MB

The reason people believe C++ is lean is that they almost never build its dependencies. They install them. Pre-built. From a package manager, an SDK installer, a vendor-shipped .lib, or the system /usr/lib. This is binary distribution, and the C++ ecosystem has depended on it for forty years, largely because building C++ from source at scale is famously miserable: no standard build system, no standard package manager, ABI landmines everywhere, and header-only libraries that recompile the world every translation unit.

Aside

Header-only ≠ free

A single innocent #include <boost/asio.hpp> can pull in 100,000+ lines of code per translation unit. Multiply by files. Multiply by templates. This is exactly the same monomorphization tax Rust pays — C++ just hides it behind ccache and pretends it isn’t there.

Rule of thumb

If you compile it, you store it.

Debug info is typically 5–20× the size of the code it describes. Templates/generics multiply that further. There is no language that escapes this — only ecosystems that pre-pay the cost for you and hand you the result.

3 · Two philosophies, one disk

Source distribution

“Here is the recipe. Bake it yourself.”

Rust/Cargo, Go modules, most of Nix, Gentoo Portage, Haskell/Cabal.

  • + Reproducible — same source, same flags, same binary.
  • + Cross-compile to anything you have a toolchain for.
  • + LTO, PGO, custom target-cpu, feature flags all work.
  • + Auditable. You can literally read every line that runs.
  • − First build is slow and enormous.
  • − target/ grows without bound.
  • − CI needs disk, RAM, and patience.
Binary distribution

“Here is a cake. Please don’t ask.”

Python wheels, npm (native modules), Conan/vcpkg (binary mode), apt/dnf, Homebrew bottles, PyTorch, CUDA.

  • + Install in seconds, not hours.
  • + No toolchain required on the user’s machine.
  • + Lets non-experts consume complex native code.
  • − One wheel per (OS × arch × Python × CUDA × ABI).
  • − Vendors bundle every .so they touched, “just in case.”
  • − The same 2 GB of CUDA lives in 14 different venvs.
  • − You cannot patch, audit, or recompile with new flags.

Notice how the trade-offs are almost mirror images. Source distribution trades disk and time for flexibility and correctness. Binary distribution trades flexibility for speed at install time — and then, quietly, it trades your disk back anyway, in a different currency.

4 · The hidden cost of “just download the binary”

Cost #1

Combinatorial explosion

A binary must exist for every OS, every CPU arch, every ABI, every supported version of the language, and every version of every native dependency it links against. PyTorch ships roughly ~30 wheels per release. The project’s release page is measured in gigabytes.

Cost #2

Bundle-everything syndrome

Because the packager cannot assume anything about the user’s system, they ship their own libc-adjacent shims, their own OpenSSL, their own MKL, their own cuDNN, their own libjpeg. Every wheel is a miniature Linux distribution in a trench coat.

Cost #3

Duplication by venv

Each virtualenv, each Docker layer, each conda env re-downloads and re-stores the same 2 GB CUDA runtime. There is no system-wide deduplication because there is no system-wide contract about which version is “safe.”

Cost #4

Opaque supply chain

A wheel is a zip file of pre-compiled .sos someone else built on some CI machine somewhere. Reproducing it byte-for-byte is often impossible. Auditing it is a job for a reverse engineer, not a reviewer.

Cost #5

Version lock-in

Because binaries carry an ABI, upgrading Python or glibc can invalidate an entire dependency graph. This is why “just pip install” periodically ends with a 40-message Stack Overflow thread and a fresh conda environment.

Cost #6

The illusion of small

Your project directory is 12 KB. Your dependencies live somewhere else, out of sight, and therefore out of your mental model of the project. It feels lightweight. It is not. It is just tidied away.

5 · Exhibit A: pip install torch

$ pip install torch # Downloading torch-2.x-cu121… # 2.7 GB # ├─ libtorch_cuda.so (1.1 GB) # ├─ libcudnn*.so.9 (700 MB) # ├─ libcublasLt.so.12 (500 MB) # ├─ libnccl.so.2 (200 MB) # └─ everything else (200 MB) $ cat model.py import torch x = torch.randn(3, 3) print(x @ x.T) # 5 lines of code. # ~8 GB on disk once venv is set up.

*sizes approximate, vary by release

This is binary distribution at its most extreme — and, to be fair, its most successful. A researcher who has never heard the word "linker" can, in ninety seconds, import a state-of-the-art GPU tensor library and start training. That is a genuine miracle. It is also why the directory containing their five-line script is now larger than every game they own on Steam.

The interesting part is why it must be this big. PyTorch cannot assume you have CUDA. It cannot assume which version. It cannot assume cuDNN. It cannot assume a compatible libstdc++. The safe move — the only move, given the ecosystem — is to bundle everything and set RPATH to its own directory. Multiply by every venv you have ever created, and you have a working definition of modern ML disk usage.

Source-dist equivalent

You’d download a few hundred MB of source, spend 4 hours compiling CUDA kernels against your toolkit, and end up with a build/ approximately the same size as the wheel — except now you pay the CPU bill instead of NVIDIA’s CI cluster.

The honest accounting

Binary distribution doesn’t make the bytes disappear. It moves them from target/ (where you can see them) to site-packages/ (where you can’t), and it copies them once per environment.

6 · Practical mitigations, per ecosystem

Rust / Bevy ▸
  • Set CARGO_TARGET_DIR to a shared path so every project reuses one target/.
  • Use sccache or cargo-cache to prune old artifacts.
  • Enable Bevy’s dynamic_linking feature during development — a link, not a monomorphize.
  • Use the mold or lld linker; strip debug info you don’t use with split-debuginfo = "unpacked".
  • Accept that target/ is a cache, not a deliverable. Delete it whenever you feel like it.
C / C++ ▸
  • ccache / sccache for compile caching.
  • Precompiled headers, unity builds, or modules (C++20) to fight the header explosion.
  • -g1 or -gsplit-dwarf to keep debug info manageable.
  • Use vcpkg/Conan in binary cache mode for dependencies; source-build only what you own.
Python / PyTorch ▸
  • Use uv or pip's shared cache; better yet, hard-link across venvs.
  • Pick a slim wheel variant (torch vs torch-cpu) when you don’t need CUDA.
  • In Docker, install big wheels in a dedicated layer so they cache across image rebuilds.
  • Consider conda/mamba for real system-level dedup of CUDA and friends.

7 · A verdict, of sorts

The 4 GB Bevy target/ is not a bug. It is the visible face of an honest bargain: you get every line of every dependency, compiled exactly for your machine, with a cache that makes the second build nearly instantaneous. The C++ project you compare it to looks smaller only because someone else already paid the bill, on different hardware, months ago, and shipped you the leftovers.

Binary distribution is not evil — without it, there would be no modern ML, no easy CUDA, no brew install anything. But it is not free either. It just charges you in a currency you don’t notice: duplicated multi-gigabyte libraries scattered across every environment on your machine, an opaque supply chain, and a build you cannot reproduce.

So the next time du -sh target/ makes you wince, remember: you are not paying more than the C++ or Python developer next to you. You are just paying visibly. And in software, being able to see the cost is usually the first step to controlling it.

TL;DR

  1. Bevy compiles ~400 crates from source, in debug, with symbols.
  2. C++ isn’t smaller — it just installs binaries instead of building them.
  3. Binary distribution moves the bytes; it doesn’t delete them.
  4. PyTorch is the reductio ad absurdum: 5 lines of code, 8 GB of dependencies.
  5. Pick your poison: slow builds, or 14 copies of CUDA.
